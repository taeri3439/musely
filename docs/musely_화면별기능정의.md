## SC-01. 홈

**경로** `/` · **진입** 앱 첫 진입 · **담당 기능** PRF-03, REC-01

### 인터랙션 흐름

| # | 트리거 | 동작 | API | 결과 |
|---|---|---|---|---|
| 1 | 화면 진입 | 프로필 조회 | `GET /api/profiles/{id}` | 있으면 요약 카드, 없으면 빈 상태 |
| 2 | 트랙 칩 탭 | 선택 상태 변경 | — (클라이언트) | 선택 표시, 추천받기 활성화 |
| 3 | [추천받기] | 추천 요청 생성 | `POST /api/recommendations` | 202 + jobId 수신 → SC-03 이동 |
| 4 | [수정] | 프로필 수정 진입 | — | SC-02 수정 모드 |
| 5 | [기록] | 히스토리 진입 | — | SC-05 |

### 화면 로직

- 프로필이 없으면 트랙 선택과 추천받기를 **아예 숨기고** 프로필 만들기 CTA만 노출한다. 비활성 버튼을 보여주는 것보다 할 일이 명확하다.
- `preferredScentFamilies`가 비어 있으면 `향수`·`둘 다` 칩을 비활성화하고, 그 이유("향 취향을 추가하면…")를 칩 아래에 표시한다. 비활성만 시키고 이유를 안 적으면 사용자가 막힌다.
- `POST /api/recommendations`는 202를 즉시 주므로 버튼 로딩은 길어야 1초다. 이게 오래 걸린다면 백엔드가 ai-core 응답을 기다리고 있다는 뜻이고, 그건 설계 위반이다.

### 완료 기준

- [ ] 프로필 없는 상태로 진입하면 프로필 만들기 유도가 보인다
- [ ] 향 취향 미입력 시 향수·둘 다가 선택 불가이고 그 이유가 화면에 있다
- [ ] 추천받기를 누르면 1초 안에 SC-03으로 넘어간다
- [ ] 요청 실패 시 버튼이 원상복구되고 에러 메시지가 뜬다

## SC-02. 프로필 입력

**경로** `/profile` · **진입** SC-01의 [프로필 만들기] 또는 [수정] · **담당 기능** PRF-01, PRF-02, PRF-04, PRF-05, PRF-06

### 인터랙션 흐름

| # | 트리거 | 동작 | API | 결과 |
|---|---|---|---|---|
| 1 | 수정 모드 진입 | 기존 프로필 조회 | `GET /api/profiles/{id}` | 모든 선택값이 채워진 상태 |
| 2 | 피부타입 선택 | 필수값 충족 | — | [다음] 활성화 |
| 3 | 성분 자유 입력 후 쉼표 | 칩 변환 | — (클라이언트) | 칩 생성, × 로 삭제 가능 |
| 4 | [다음] | 스텝2 이동 | — | **서버 저장 안 함** |
| 5 | [건너뛰기] | 향 필드 비우고 저장 | `POST` 또는 `PUT /api/profiles` | SC-01 복귀 |
| 6 | [저장] | 전체 저장 | `POST` 또는 `PUT /api/profiles` | SC-01 복귀 |

### 화면 로직

- **스텝1→2 이동 시 서버에 저장하지 않는다.** 마지막에 한 번만 저장한다. 중간 저장하면 향 정보가 빠진 불완전 프로필이 DB에 남고, 그 상태로 이탈한 사용자를 처리하는 로직이 또 필요해진다.
- 신규는 `POST`, 수정은 `PUT`. 프론트가 진입 모드를 알고 분기한다.
- 기피 성분 섹션과 사용 중 성분 섹션은 **용도가 반대**다(전자는 제외용, 후자는 주의 안내용). 각 섹션의 도움말 문구로 구분을 명확히 한다.
- 저장 실패 시 입력값을 유지한다. 폼을 비우면 사용자가 다시 다 입력해야 한다.

### 완료 기준

- [ ] 피부타입 미선택 시 [다음]이 눌리지 않는다
- [ ] 쉼표 입력 시 칩이 생기고 × 로 개별 삭제된다
- [ ] 건너뛰기로 저장해도 화장품 추천은 정상 동작한다
- [ ] 수정 모드 진입 시 기존 값이 전부 채워져 있다
- [ ] 저장 실패해도 입력값이 남아 있다
- [ ] 스텝1에서 스텝2로 갈 때 네트워크 요청이 발생하지 않는다

## SC-03. 추천 진행

**경로** `/recommend/:jobId` · **진입** SC-01의 [추천받기] · **담당 기능** REC-02, REC-06, REC-10, REC-11

**이 화면이 비동기 구조의 핵심이다.** 다른 화면은 평범한 CRUD 화면이지만 여기만 폴링 로직이 들어간다.

### 인터랙션 흐름

| # | 트리거 | 동작 | API | 결과 |
|---|---|---|---|---|
| 1 | 화면 진입 | 폴링 시작 (1초 간격) | `GET /api/recommendations/jobs/{jobId}` | 상태 수신 |
| 2 | `status = RUNNING` | 단계 갱신 | (동일) | trace 기반 4단계 표시 |
| 3 | `status = DONE` | 폴링 중단 | — | SC-04로 자동 이동 |
| 4 | `status = DONE` · 결과 0건 | 폴링 중단 | — | **SC-04의 0건 상태로 이동** — ai-core는 0건을 `FAILED`로 주지 않는다 |
| 5 | `code = TIMEOUT` 또는 60초 경과 | 폴링 중단 | — | 타임아웃 UI + [다시 시도] |
| 6 | 그 외 `FAILED` | 폴링 중단 | — | 오류 UI + [다시 시도] |
| 7 | [취소] | 폴링 중단 | — | SC-01 복귀 (job은 버림) |
| 8 | 화면 이탈 | 폴링 정리 | — | 타이머 해제 |

### 단계 표시 매핑 (REC-06)

ai-core가 job 응답의 `steps[]`로 내려주고, **문구(`label`)까지 이미 한글로 담겨 있다.**
프론트에서 내부 노드명을 매핑하지 않는다.

| `steps[].key` | `steps[].label` (그대로 출력) |
|---|---|
| `profile` | 프로필 분석 |
| `search` | 조건에 맞는 제품 찾기 |
| `conflict` | 성분 조합 검수 (향수 트랙에는 이 단계가 없어 `skipped`) |
| `commentary` | 추천 이유 작성 (후보 0건이면 `skipped`) |

`steps[].status`는 `pending` · `running` · `done` · `skipped` 네 가지다. `skipped`는
흐리게 처리하고 완료 체크를 붙이지 않는다.

> ai-core 플랜의 `CurationState.trace`와 혼동하지 말 것. `trace`는 에이전트별 소요시간과
> 검색 쿼리를 담는 **내부 디버깅용**이고, 화면에 쓰는 건 `steps`다.

### 화면 로직

- **폴링 정리를 반드시 구현한다.** 화면을 벗어났는데 타이머가 살아 있으면 백그라운드에서 계속 요청이 나간다. React라면 `useEffect` cleanup에서 `clearInterval`.
- **후보 0건은 에러가 아니다.** 조건이 너무 빡빡했을 뿐 시스템은 정상 동작했다. 그래서 ai-core는 0건을 `FAILED`로 주지 않고 `status: DONE` + 빈 배열 + `blockedBy`(걸린 조건 목록)로 준다. 프론트는 오류 화면이 아니라 결과 화면의 0건 상태로 보낸다. 이걸 에러로 처리하면 사용자는 앱이 고장 난 줄 안다.
- 진행률 바는 실제 진행도가 아니라 단계 기반이다. 마지막 단계에서 100%에 도달시키지 말고 90% 근처에서 멈춘 뒤 완료 시 전환한다.
- 60초 상한은 프론트 책임이다. ai-core에도 30초 상한이 있지만 네트워크·백엔드 지연이 더해질 수 있어 양쪽 다 필요하다.

### 완료 기준

- [ ] 폴링이 1초 간격으로 돈다
- [ ] 화면을 벗어나면 폴링이 즉시 멈춘다
- [ ] 60초 경과 시 자동으로 타임아웃 화면이 된다
- [ ] 단계 문구에 내부 노드명(`ingredient_matcher` 등)이 노출되지 않는다
- [ ] 결과 0건(`DONE` + 빈 배열)이 오류 화면이 아니라 결과 0건 화면으로 간다
- [ ] 취소 후 홈으로 돌아가면 더 이상 요청이 나가지 않는다

## SC-04. 추천 결과

**경로** `/recommendations/:id` · **진입** SC-03 완료 / SC-05 카드 탭 · **담당 기능** REC-07, REC-08, REC-09, FBK-01, FBK-02

### 인터랙션 흐름

| # | 트리거 | 동작 | API | 결과 |
|---|---|---|---|---|
| 1 | 화면 진입 | 추천 결과 조회 | `GET /api/recommendations/{id}` | 요약·주의·제품 목록 |
| 2 | `relaxationLevel > 0` | 완화 배너 표시 | — | 상단 안내 배너 |
| 3 | `cautions` 있음 | 주의 카드 표시 | — | severity별 스타일 |
| 4 | `items` 0건 | 빈 상태 표시 | — | 걸린 조건 + [조건 수정하기] |
| 5 | [좋아요]/[아쉬워요] | 평가 저장 | `POST /api/feedback` | 버튼 비활성 + Toast |
| 6 | [조건 바꿔서 다시 받기] | 프로필 수정 진입 | — | SC-02 수정 모드 |

### 렌더링 규칙

| 조건 | 처리 |
|---|---|
| `cautions` 비어 있음 | 주의 영역 **전체를 렌더링하지 않음** (빈 카드 금지) |
| 향수 미요청 (`track = cosmetic`) | 향수 섹션 렌더링하지 않음 |
| `relaxationLevel = 0` | 완화 배너 렌더링하지 않음 |
| `items` 0건 | 요약·주의·제품 영역 대신 빈 상태 하나만 |
| 이미 평가함 | 두 버튼 모두 비활성, 선택한 쪽 강조 |

### 화면 로직

- **모든 제품 카드에 추천 이유 한 줄이 반드시 붙는다.** 이게 이 서비스의 존재 이유고, 빠지면 그냥 제품 목록이 된다. 백엔드 응답에 `note`가 비어 오면 그건 ai-core 버그로 취급한다.
- 주의 배지는 색과 **텍스트 라벨을 함께** 쓴다(`[⚠ 주의]`, `[⛔ 피하세요]`). 색만으로 구분하면 색각 이상 사용자가 구분할 수 없다.
- `source`·`confidence`는 반드시 표시하되 캡션 크기로 작게. 있는 게 중요하지 눈에 띌 필요는 없다.
- 0건 화면에서 **어떤 조건이 걸렸는지 보여준다.** "결과 없음"만 있으면 사용자가 뭘 고쳐야 할지 모른다.

### 완료 기준

- [ ] 모든 제품 카드에 추천 이유가 있다
- [ ] 주의 배지에 색 외에 텍스트 라벨이 있다
- [ ] 주의사항 0개일 때 빈 카드가 아니라 영역 자체가 없다
- [ ] 0건일 때 걸린 조건이 표시되고 수정 경로가 있다
- [ ] 피드백 제출 후 다시 누를 수 없다
- [ ] SC-05에서 진입해도 동일하게 렌더링된다 (읽기 전용)

## 03. 전 화면 공통 (CMN-02, CMN-03, CMN-04)

### 에러 코드 → 사용자 문구 (CMN-02)

| code | 사용자에게 보이는 문구 | 다음 행동 |
|---|---|---|
| `TIMEOUT` | 시간이 오래 걸리고 있어요 | [다시 시도] |
| `LLM_ERROR` | 추천 이유를 만들지 못했어요 | [다시 시도] |
| `INTERNAL` | 문제가 생겼어요 | [다시 시도] |
| `JOB_NOT_FOUND` | 요청을 찾을 수 없어요 | [처음으로] |
| `VALIDATION_ERROR` | (사용자에게 보이면 안 된다) | 개발 중에만 발생 |
| 네트워크 오류 | 연결이 불안정해요 | [다시 시도] |

**모든 에러 화면에는 다음 행동 버튼이 하나 있어야 한다.** 메시지만 있고 나갈 길이 없으면 사용자가 갇힌다.

**결과 0건은 이 표에 없다.** 에러 코드가 아니라 `status: DONE` + 빈 배열로 오는 정상
응답이다. 화면 문구는 "조건에 맞는 제품을 찾지 못했어요" + [조건 수정하기]이고, 위치는
에러 화면이 아니라 SC-04의 빈 상태다.

### 4가지 상태 (CMN-04)

모든 화면에 대해 아래 네 가지를 다 구현한다.

| 상태 | 특히 놓치기 쉬운 곳 |
|---|---|
| 기본 | — |
| 로딩 | SC-01 프로필 카드, SC-05 목록 |
| 빈 상태 | SC-04 0건, SC-05 기록 없음, SC-01 프로필 없음 |
| 에러 | SC-03 타임아웃, SC-02 저장 실패 |

### 반응형 (CMN-03)

| 구간 | 규칙 |
|---|---|
| ~479px | 1열, 좌우 여백 16px |
| 480~1023px | 1열, 본문 최대폭 560px 중앙 |
| 1024px~ | SC-04 제품 카드 2열, 본문 최대폭 840px |

## 05. 개발 순서 제안

화면 단위로 끝까지 만들되, 아래 순서를 권한다.

| 순서 | 화면 | 이유 |
|---|---|---|
| 1 | **SC-02 프로필 입력** | 순수 CRUD라 ai-core 없이도 완성된다. 백엔드가 바로 시작 가능 |
| 2 | **SC-01 홈** | SC-02 결과를 보여주는 화면. 추천 요청까지 붙이면 mock으로 SC-03 진입 확인 가능 |
| 3 | **SC-03 추천 진행** | mock 서버의 `_mock_delay`로 로딩·타임아웃·에러를 전부 테스트 |
| 4 | **SC-04 추천 결과** | mock의 고정 응답으로 레이아웃 완성 → 나중에 실제 ai-core로 교체만 |
| 5 | SC-05 히스토리 | 여유 있으면 |

**핵심은 1~4를 전부 mock 서버로 끝낸다는 것이다.** 실제 ai-core 연동은 3주차에 URL 하나만 바꾸면 되는 상태를 만들어두면, 나연님 쪽 진행 속도와 무관하게 프론트·백엔드가 완성된다.
